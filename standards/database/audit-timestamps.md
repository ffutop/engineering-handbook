# 数据库审计时间规范

- 类型：技术
- 状态：Proposed
- 负责人：仓库维护者（合入前确认）
- 适用范围：采用 PostgreSQL、Java 与 Flyway 的项目中的业务表及写入路径
- 面向读者：架构师、开发者、数据库维护者与评审者
- 本文规范什么：审计时间的字段、语义、维护、豁免与存量迁移
- 不规范什么：完整审计日志设计、业务事件时间模型及数据保留期限
- 规范来源或替代关系：本文件为审计时间规则的唯一来源；迁移过程引用 Flyway 数据库迁移标准
- 最后确认日期：待维护者确认；编写日期为 2026-10-27
- 实现情况与验证证据：本文件定义要求，未提供已验证的实现模板；项目采用情况须分别验证
- 未决项：维护者确认并发布；采用项目确定时间来源、维护机制和更新策略

## 1. 目标与采用

审计时间用于判断记录何时首次持久化、何时发生后续持久化变更。字段存在但维护不完整，会让排障、数据核对和变更判断产生错误结论；因此字段定义与全部写入路径的行为必须一起验证。

规则强度、版本固定与例外管理遵循[规范治理标准](../documentation/standard-governance.md)。采用项目在 `ENGINEERING_STANDARDS.md` 固定本标准版本、适用模块、执行与评审负责人、验证入口，并声明第 3 节中的项目策略。其他技术栈采用时，须明确等价类型映射和验证依据，不直接照搬 Java 或 PostgreSQL 类型。

## 2. 强制规则

### 2.1 字段与适用范围

可修改的业务表必须包含下列字段，包括具有独立生命周期的关联表、配置表和字典表：

| 数据库字段 | 数据库类型 | Java 字段 | Java 类型 | 约束 |
|---|---|---|---|---|
| `created_at` | `TIMESTAMPTZ` | `createdAt` | `OffsetDateTime` | 非空，创建后不可通过常规写入修改 |
| `updated_at` | `TIMESTAMPTZ` | `updatedAt` | `OffsetDateTime` | 非空，随持久化变更维护 |

字段是否必需取决于数据是否允许修改，不取决于表名或是否为关联表。只追加且不可修改的事件、版本快照和审计日志必须包含非空的 `created_at`，可省略 `updated_at`；后续允许修改时，必须补齐字段与维护机制。

临时表、可重建的派生表和框架管理表可豁免。豁免必须在所属模块设计文档或迁移脚本中列明表、原因及适用条件，不得以“关联表”为由自动豁免。超出上述范围的偏离按规范治理标准记录例外。

### 2.2 时间语义与变更边界

`created_at` 表示记录在本系统首次持久化的时间，不是业务发生时间或事务提交时间。普通新增记录时，`updated_at` 必须与 `created_at` 相同。后续业务数据发生持久化变更时，必须同步维护 `updated_at`，包括软删除、状态变更和关联关系调整。

没有产生实际数据变化的重复提交或更新，可以不修改 `updated_at`。项目必须统一选择“仅实际数据变化时更新”或“凡执行行更新就更新”，不得由各写入入口自行解释。采用前者时，必须明确参与变化判断的字段，避免将审计时间自身纳入判断造成无意义更新。

upsert 插入分支遵循新增规则；冲突更新分支必须保留原 `created_at`，并按统一更新策略维护 `updated_at`；未写入任何记录的冲突分支不应制造时间变更。

数据导入按本系统首次持久化记录审计时间；需要保留源系统时间时另设字段。存量回填和经评审的数据修复按第 4 节处理，不得借此允许日常写入覆盖历史时间。

### 2.3 全部写入路径一致

维护机制必须覆盖应用、批量任务、脚本、直接 SQL、upsert 等全部实际写入路径。仅设置建表默认值不能维护更新行为；仅覆盖 ORM 写入的自动填充也不能证明满足本规则。

所有常规入口都必须保护 `created_at`，并在相应数据写入的同一事务中维护 `updated_at`。不得依赖异步补写才能满足本规则。客户端传入的审计字段不得未经控制地成为数据库最终值。

推荐使用数据库统一维护，减少多入口实现不一致。选择应用或其他机制时，项目必须说明如何覆盖并约束其他入口，提供逐项验证证据。使用数据库生成值时，必须明确 Java 对象何时获取最终值，避免将写入前的值作为持久化结果返回。

### 2.4 与业务时间、审计记录的边界

申请、处理、挂靠生效、授权、终止等业务事件时间必须保留各自字段，不得使用 `created_at`、`updated_at` 替代。

两个审计时间字段不能替代操作人、变更内容、变更原因等审计记录，也不能单独证明记录的完整变更历史。需要完整审计时，项目须另行设计。

`updated_at` 不保证每次修改都严格递增，不得用作乐观锁版本号或作为增量同步不漏数据的唯一依据；相应并发控制与同步协议由项目另行设计。

## 3. 项目必须决定的策略

| 策略 | 项目声明的内容 |
|---|---|
| 时间来源 | 使用数据库还是应用时钟；具体函数或时钟接口及其语义 |
| 更新策略 | 仅实际变化时更新，还是凡执行行更新就更新；前者列明比较范围 |
| 维护机制 | 数据库触发器、公共写入组件或其他实现；全部入口及责任人 |
| 精度与传输 | 数据库与 Java 往返精度、接口时间格式及展示时区 |
| 特殊修复 | 历史回填或修复如何受控写入时间、保留记录并恢复常规保护 |

推荐以数据库作为统一时间来源。选择 PostgreSQL 事务时间时，同一事务内多次修改可以得到相同时间；它表示事务开始时间，不能表述为每条语句的实际执行时间。项目如选择语句时间或实际时钟时间，须统一使用并验证新增两个字段相等的要求。

`TIMESTAMPTZ` 存储时间点，不保留输入时的原始时区名称或原始偏移量。需要保留这些业务信息时必须另设字段。接口推荐采用带偏移量的 ISO 8601 格式并统一输出 UTC，展示时按明确的用户或业务时区转换；不得依赖服务器默认时区解释时间。

## 4. 存量表与 Flyway 迁移

新建表必须直接满足本规则。存量表补齐必须新增 Flyway migration，禁止修改已经发布的迁移补字段；已在共享环境执行的迁移同样不可修改。迁移命名、不可变性、分阶段演进和恢复要求遵循 [Flyway 数据库迁移标准](flyway-migration.md)，本文不另设迁移命名规则。

迁移评审必须明确：

- 需要补齐的表与字段、豁免表及原因；
- 每个历史字段的回填来源、推导方法、覆盖范围及无法还原时的估算口径；
- 新旧应用共存期间的写入保障、并发写入与回填的协调方式，以及非空约束生效顺序；
- 大批量回填的执行责任、事务边界、校验与失败恢复方式。

优先使用可信的历史记录或既有时间字段回填，但业务事件时间不能未经语义核对就当作审计时间。无法还原时必须说明估算值代表什么、哪些记录受影响以及证据位置；不得把回填执行时间表述为真实历史时间，也不得把估算的创建时间描述为准确历史事实。

先补可空字段、再回填、最后添加非空约束时，必须在过渡期间保障新写入，避免回填结束后继续产生空值。回填不得覆盖已由常规写入正确维护的时间；需要绕过常规字段保护时，必须限定操作范围并验证结束后保护已恢复。

## 5. 评审与验证

字段与约束由 schema 检查验证，实际维护行为由数据库集成测试验证。采用项目须提供以下证据，并与被验证的代码及迁移版本关联：

| 场景 | 验证结果 |
|---|---|
| 适用表与豁免检查 | 字段、数据库类型、非空约束和 Java 映射正确；豁免有依据 |
| 新增记录 | 两个审计字段非空且相等，或符合只追加表的字段要求 |
| 修改与软删除 | `created_at` 保持原值；`updated_at` 按项目策略维护 |
| 重复更新 | 无实际变化时的行为符合统一策略 |
| 多入口写入 | 应用、批量任务、脚本、直接 SQL 等实际入口分别验证 |
| upsert | 插入、冲突更新和冲突不写入分支分别符合规则 |
| 常规入口覆盖审计字段 | 不能擅自改写创建时间或绕过更新时间维护 |
| 事务与类型往返 | 回滚不遗留变更；时间函数语义、精度及跨偏移量读取符合声明 |
| 存量升级 | 从代表性旧数据升级，回填依据可追溯，非空约束成立，并发写入不破坏结果 |

测试更新时间时必须考虑项目所选时间函数和存储精度，不得统一断言每次写入的时间都严格大于前一次。仅检查字段存在、默认值存在或 ORM 注解存在，不足以通过评审。
