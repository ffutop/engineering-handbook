# Flyway 数据库迁移标准

本标准约束使用 Flyway 管理关系型数据库结构与受控基础数据的团队项目。它定义跨项目的最低要求；数据库拓扑、外键策略和发布方式等架构选择，由每个项目在 `ENGINEERING_STANDARDS.md` 和 ADR 中声明。

规则分级、版本固定、例外与升级遵循[规范治理标准](../documentation/standard-governance.md)。

## 1. 项目采用声明

每个采用本标准的项目在仓库根目录创建 `ENGINEERING_STANDARDS.md`，至少声明：

| 字段 | 要求 |
|---|---|
| 标准地址 | 指向本文件的仓库 URL 或本地开发路径 |
| 标准版本 | 已发布的不可变 Git tag，或尚未发版时固定 commit SHA；本地试用可暂用 `unreleased` |
| 执行模型 | 单一实例，或按 schema / 模块创建多个实例 |
| 版本号格式 | 无既有规则的项目采用 2.3 的正式命名规则；已有规则的项目记录并严格沿用原规则，同时声明时间戳时区（如适用） |
| 外键策略 | 允许、限制或禁止，以及 ADR 地址 |
| 执行时机 | 应用启动、发布 Job 或独立迁移流程 |
| 迟到迁移策略 | 合流与发布检查负责人、共享环境执行记录的来源，以及 `outOfOrder` 的使用策略 |
| 大批量回填策略 | 任务归属、事务边界和审计方式 |

项目不得长期引用 handbook 的分支名。升级标准版本必须通过项目自身的评审，并同时完成新规则要求的代码、CI 或文档适配。

## 2. 强制规则

### 2.1 已发布迁移不可变

任何已在共享环境执行的版本化迁移不得修改或删除，包括文件名、版本号、注释、格式和影响执行的同名脚本配置。Flyway 使用 checksum 验证内容；修复必须新增后续迁移并向前修复。

### 2.2 文件职责清晰

一个版本化迁移只完成一项逻辑变更。DDL 与种子数据分别放入文件；可重复对象（视图、函数、存储过程）使用 `R__{description}.sql`，并保证可安全重复执行。

### 2.3 命名

版本化迁移的命名必须遵守以下两条规定，既有项目规则优先：

1. **正式命名规则**：无既有命名规则的项目，版本化迁移必须使用 `V{X.Y.Z.yyyyMMddHHmmss}__{description}.sql`。其中 `X.Y.Z` 为编号分配时预期的目标发布版本；`yyyyMMddHHmmss` 为编号分配时间，14 位，依次表示年、月、日、时（24 小时制）、分、秒，采用项目声明的统一时区。例如 `V1.4.0.20261002173000__create_customer.sql`。首次在共享环境执行后，编号冻结；发布改期不再改写编号，实际发布归属由发布记录维护。
2. **既有规则兼容**：项目已有命名规则时，必须严格沿用原规则，包括新增迁移；不得因采用本标准而切换格式、混用新规则或重命名、重编号历史文件。项目在采用声明中记录原规则及示例，CI 按原规则检查。

描述使用小写英文和下划线，以动作说明意图，例如 `create_customer`、`add_status_column`、`seed_default_roles`。同一迁移序列内版本号必须唯一；时间戳不能替代重复版本检查，版本排序与执行顺序仍须按 Flyway 的版本比较规则验证。

若项目使用 Flyway Community Edition，禁止提交 `U{version}__{description}.sql`，因为 Undo 脚本不会被执行。

### 2.4 数据变更可安全重跑

种子数据和可预见需要重跑的 DML 必须具备幂等性。例如 PostgreSQL 使用 `INSERT ... ON CONFLICT DO NOTHING` 或有明确覆盖语义的 UPSERT。历史上的非幂等迁移不可为此回改。

### 2.5 非事务语句

PostgreSQL 的 `CREATE INDEX CONCURRENTLY`、`DROP INDEX CONCURRENTLY` 和 `REINDEX CONCURRENTLY` 不能运行在事务块中。包含这些语句的迁移必须提供同名脚本配置文件。例如 `V1.4.0.20261002173000__create_customer_index.sql` 对应 `V1.4.0.20261002173000__create_customer_index.sql.conf`：

```properties
executeInTransaction=false
```

SQL 注释不能替代 Flyway 脚本配置。项目须确认所用 Flyway 与数据库版本支持该配置，并在集成测试中验证实际执行方式。

此类文件只应包含该项非事务操作。执行失败不会自动回滚，评审中必须确认清理和恢复步骤。

### 2.6 向后兼容的演进

对已运行系统的结构演进优先采用“新增结构 → 回填或双写 → 切换读取 → 废弃旧结构”的阶段式路径。直接删除表或列、重命名表或列、收窄类型或约束，都必须作为项目明确评审的例外，并有数据备份、回滚和发布计划。

新增非空列到已有表时，必须提供安全默认值，或先新增可空列、完成回填后再添加非空约束。

### 2.7 安全与运行

生产环境必须禁用 `flyway clean`。多实例并发迁移依赖 Flyway 的 schema history 锁；只有观察到锁等待问题时才按项目运行模型调整重试配置。

大批量数据修复不应依赖单个 Flyway 脚本中的循环伪造分批提交。应使用可观测的一次性任务，明确每批事务边界、限流、停止条件和变更记录。

### 2.8 迟到迁移与分支合流

迁移编号是身份与默认排序依据，不是依赖正确性的证明。迟到迁移指：在某个目标环境尚未执行，但其版本号低于该环境已成功执行的最高版本号的迁移。是否迟到必须逐环境判断，不能仅根据 Git 合入时间、文件时间戳或应用发布版本判断。

处理迟到迁移必须同时保证：已执行迁移身份不变；实际执行顺序满足结构和数据依赖；空库初始化与已有环境升级均达到预期结构和受控数据状态。否则可能出现漏执行、重复变更，或同一发布在不同环境产生不同结果。

合流评审和发布前检查必须核对候选迁移集合与相关共享环境的 schema history，记录迟到迁移、已执行范围及依赖关系，并按以下边界处理：

- **尚未在任何共享环境执行**：允许根据目标发布与依赖关系重新编号，并同步调整同名脚本配置；新编号必须唯一，且位于所依赖迁移之后。随后重新验证完整迁移链和受影响环境的升级路径。单纯提高编号不能证明 SQL 在新顺序下仍然正确。
- **已在任一共享环境执行**：保留原文件与编号，不得复制同一变更到高版本脚本后让所有环境再次执行。若迟到环境仍可安全执行原迁移，可按项目声明的 `outOfOrder` 策略处理；否则须制定包含原迁移处置、后续修复和各环境执行路径的专项合流方案，由迁移负责人评审并验证。新增后续迁移不能自动解决原迁移在其他环境尚未执行的问题。

`outOfOrder` 默认保持 `false`。使用 `outOfOrder=true` 只允许低版本迁移补执行，不保证依赖成立或结果一致；必须明确受影响环境、待补执行集合和配置生效范围，并验证原迁移在当前结构与代表性数据上可安全执行。不得仅以开启该配置、改写编号或通过 `repair` 掩盖差异作为处理完成的依据。

例如，共享环境已执行 `V1.5.0.20261002100000`，随后合入 `V1.4.1.20261002110000`：后者虽然时间戳更晚，仍属于低版本迁移。若它从未在共享环境执行，可在确认依赖后重新编号；若已在另一共享环境执行，则必须保留身份并验证两种执行顺序，不能直接改名。

## 3. 项目必须决定的策略

以下不是本标准的默认结论，项目必须在采用声明或 ADR 中作出选择：

- 单一版本序列还是每 schema / 模块独立版本序列；
- 是否使用数据库外键，以及一致性责任归属；
- 跨 schema 或跨服务的种子数据登记方式；
- 是否允许物理清理废弃结构，以及其审批与维护窗口；
- 迁移由应用启动、发布 Job 或独立流水线运行；
- 测试和演示数据的隔离方式。
- 是否允许迟到迁移补执行，以及 `outOfOrder` 的配置范围、评审责任和多发布线合流方式。

## 4. 评审与 CI

项目 CI 必须依据采用声明检查新增迁移的命名：无既有规则的项目检查 `X.Y.Z` 为非负整数三段、时间戳为 14 位且日期时间有效、描述符合小写英文和下划线要求；已有规则的项目检查是否严格沿用原规则。CI 还至少检查重复版本号、非事务语句对应的 `.sql.conf` 配置，以及对已发布迁移的修改。数据库集成测试必须在临时数据库执行完整迁移链；对已有系统的变更，还必须从当前生产版本对应的结构与代表性数据升级，验证数据保留和新旧应用兼容性；含种子数据的变更应验证目标状态可重复得到。

无法可靠静态判断的规则，例如破坏性变更、大批量回填和跨模块数据所有权，必须在 PR 模板或人工评审清单中确认。

重复版本检查必须按 Flyway 解析后的版本比较，不能仅比较文件名。合流 CI 应依据有来源和采集时间的共享环境执行记录识别新增低版本迁移；发布前必须核对目标环境的实际 schema history，发现未处理的迟到迁移时停止迁移与应用发布。CI 使用的快照不能替代发布前的实际状态检查。

存在迟到迁移时，评审记录必须包含处理方式、受影响环境及验证证据。集成测试除空库完整迁移链外，还必须覆盖受影响环境的实际已执行迁移集合与顺序，并使用代表性数据验证升级，确认最终结构、受控数据、数据保留和应用兼容性满足同一预期；仅验证文件排序或 SQL 可执行不足以通过。

## 5. 失败与恢复

迁移失败后先核对 schema history、实际结构与数据状态，停止依赖新结构的应用发布。事务回滚不能作为所有 DDL 的默认保证；非事务迁移必须定义部分成功状态的检测与清理步骤。

`repair` 只能在实际数据库已与预期一致、失败原因已消除后，由迁移负责人执行并保留操作记录；不得通过更新 checksum 掩盖已执行迁移被修改。应用回滚与数据库恢复分别制定：优先回滚到仍兼容当前结构的应用版本，数据恢复须验证备份可用性及可接受的数据损失窗口。
