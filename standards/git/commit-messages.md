# Git 提交信息规范

- 类型：技术
- 状态：Proposed
- 负责人：仓库维护者（合入前确认）
- 适用范围：采用本规范的项目中人工或工具生成的 Git 提交信息
- 面向读者：开发者、评审者与生成提交信息的工具维护者
- 本文规范什么：提交信息的内容、格式及既有规范兼容方式
- 不规范什么：分支策略、提交作者身份、签名和发布流程
- 规范来源或替代关系：本文件为提交信息规则的唯一来源；默认格式引用 Conventional Commits 1.0.0
- 最后确认日期：待维护者确认；整理日期为 2026-10-03
- 实现情况与验证证据：已提供规则与示例；尚未提供自动校验，项目采用情况须分别验证
- 未决项：维护者确认并发布版本；采用项目配置相应检查

规则分级、版本固定、例外与升级遵循[规范治理标准](../documentation/standard-governance.md)。

## 1. 目的

提交信息应让读者快速理解变更意图，并兼容仓库现有的协作方式。只保留有助于理解、检索和自动处理的结构，避免重复代码细节、堆砌格式或附加无关信息。

## 2. 基本要求

- 提交信息必须为单行，不添加正文、脚注或空行。Git 保存消息时的末尾行结束符不计为额外内容行。
- 提交信息中禁止出现 `Co-Authored-By` 字样，检查时不区分大小写。
- 描述必须准确、简洁，说明具体变更；必要时说明目的。
- 避免使用“更新代码”“修复问题”“调整内容”等无法辨认变更的描述。

单行使完整消息可直接用于提交列表和自动处理；禁止署名尾注避免工具自动追加内容。作者身份仍由 Git 元数据表达，不通过提交描述补充。格式正确不能替代内容准确，提交类型和描述应反映实际改动，不夸大功能、修复或验证结果。

## 3. 兼容已有规范

生成提交信息前，先检查仓库的贡献指南、代理指令和提交校验配置。

仓库已有明确提交规范时，遵循其类型、范围、语言和描述格式；没有明确规范时，可参考近期稳定一致的提交习惯。两者均不存在时，使用第 4 节的默认格式。历史提交只是惯例证据，不得覆盖明确规则。

单行和禁止 `Co-Authored-By` 是始终适用的要求。若仓库规则明确要求多行信息或该署名字段，应指出冲突，由维护者依据规范治理标准确定处理方式；在冲突解决前，不得自行声称同时满足两套规则。

兼容要求约束新增提交信息，不要求改写历史提交。

## 4. 默认格式

遵循 [Conventional Commits 1.0.0](https://www.conventionalcommits.org/zh-hans/v1.0.0/)，仅使用其单行标题结构：

```text
<type>[可选 scope][可选 !]: <description>
```

类型按变更意图选择：

| 类型 | 使用场景 |
|---|---|
| `feat` | 新增功能 |
| `fix` | 修复缺陷 |
| `docs` | 修改文档 |
| `refactor` | 重构，功能行为不变 |
| `perf` | 改善性能 |
| `test` | 修改测试 |
| `build` | 修改构建系统或依赖 |
| `ci` | 修改持续集成配置 |
| `style` | 仅调整代码格式 |
| `chore` | 无法归入以上类型的维护工作 |
| `revert` | 撤销既有变更 |

`scope` 仅在有助于定位变更时使用，不为凑格式添加。破坏性变更必须在冒号前使用 `!`，并在描述中说明不兼容之处。

```text
feat(auth): 支持通行密钥登录
fix(parser): 修复连续空格导致的解析失败
docs: 补充数据库迁移恢复步骤
feat(api)!: 移除旧版用户查询接口
```

Conventional Commits 允许可选正文和脚注；本规范的单行要求和禁止署名要求是额外约束，不是该外部规范本身的要求。

## 5. 采用与验证

采用项目在 `ENGINEERING_STANDARDS.md` 中记录本规范的路径和固定版本、既有提交规则或默认格式、检查入口及评审负责人。

提交前确认：格式符合仓库约定或默认格式，信息只有一行，不含 `Co-Authored-By`，描述与实际变更一致。

单行、禁用字样及已声明的格式要求由 CI 检查；本地提交钩子可提前反馈。内容准确性和破坏性变更标记由评审确认。检查必须覆盖实际写入仓库的提交信息；使用 squash 合并时，还须检查最终生成的提交信息。
