# 规范治理标准

- 类型：技术
- 状态：Proposed
- 负责人：仓库维护者（合入前确认）
- 适用范围：本 handbook 的规范及采用它们的项目
- 面向读者：项目负责人、架构师、开发者与评审者
- 本文规范什么：规则分级、采用、例外与验证
- 不规范什么：项目业务与具体架构选型
- 规范来源或替代关系：本文件为规范治理规则的唯一来源
- 最后确认日期：待维护者确认；审查日期为 2026-10-02
- 实现情况与验证证据：本次文档审查；项目采用情况须分别验证
- 未决项：维护者确认本次修订并发布不可变版本

## 1. 从目标推出规则

规范的价值是降低协作中的不确定性与失败成本。约束应能回答：保护什么结果、适用于什么条件、由谁执行、用什么证据判断满足。无法回答的条款，应补充依据、降为建议或移除。

| 层次 | 含义 | 使用方式 |
|---|---|---|
| 强制要求（必须、禁止） | 在适用范围内保护正确性、安全或跨系统契约 | 有检查证据；偏离须记录例外 |
| 推荐策略（应、优先、推荐） | 常见条件下成本较低的实现路径 | 可选择其他路径并说明理由 |
| 项目决策（由项目声明） | 取决于业务、负载或运行环境的取舍 | 指定负责人，给出配置或 ADR |
| 参考模板 | 一个实现示例 | 适配并验证后采用，不等于已满足规范 |

新增强制要求时，在条款附近或评审说明中写明失败场景与验证方式。不得仅因工具方便就将项目选型变成跨项目义务。

## 2. 采用与升级

项目在根目录 `ENGINEERING_STANDARDS.md` 统一记录采用情况，各专项标准只补充自己的字段：

- 标准路径、不可变 Git tag 或 commit SHA，以及适用组件和环境；
- 执行与评审负责人、检查入口及证据位置；
- 项目必须决定的策略及其 ADR；
- 例外、风险补偿措施、责任人、复核日期和退出条件。

正式采用优先引用已发布 tag；没有发布版本时可固定 commit SHA。`unreleased` 仅供试用，并须说明结束条件。升级通过项目评审，同时核对模板差异、迁移成本与既有消费者兼容性，不自动随 handbook 分支更新。

适用范围不满足时标为“不适用”并说明原因，不制造空检查。项目规模不影响安全与正确性要求，但可以合并文档、采用更简单的验证工具。

## 3. 冲突与例外

适用的外部强制约束和已确认的业务安全要求优先；项目已采用版本中的强制要求其次；项目 ADR 和配置在授权的选择空间内细化规则；参考模板不能覆盖正文。目标之间冲突时由相关负责人明确选择、影响与验证依据，不靠未记录的惯例处理。

无法满足强制要求时，按项目声明的评审责任确认限时例外，记录受影响规则与替代控制。例外不是永久豁免，复核到期须关闭或重新评审。

## 4. 验证与维护

- 静态可判定的要求由 CI 检查；运行行为由集成测试或演练确认；业务取舍由负责人评审。检查结果必须与实际版本关联。
- 已有数据库测试同时覆盖空库与升级路径；发布验证覆盖正常路径与部分成功恢复；日志验证覆盖采集、脱敏与容量边界。
- 正文和模板在同一变更中更新。未实现的控制明确标注，不把设计要求写成模板已有能力。
- 变更规则时记录受影响的项目策略、模板与验证方式。定期删除无法解释用途、无人执行或与其他规则重复的约束。
