# 文档治理标准

本标准定义团队项目中设计、架构和工程文档的最低治理要求。项目的目录结构、工具和审批流程可自行决定，但不得与本标准冲突。

## 1. 规范来源

每个项目必须为以下范围指定唯一的现行规范来源：

| 范围 | 规范内容 |
|---|---|
| 领域 | 术语、对象、状态和跨模块边界 |
| 产品 | 用户、流程、业务规则和验收边界 |
| 技术 | 数据结构、接口、部署和实现约束 |
| 决策 | 方案选择的理由、代价和替代关系 |

一条规则只能有一个现行规范来源。其他文档可以引用或解释该规则，但不得给出相冲突的版本。

## 2. 文档状态

文档只使用以下状态：

- `Proposed`：待确认。
- `Accepted`：已确认，尚未完全实现。
- `Implemented`：已实现，仍为当前规则。
- `Superseded`：已被替代，必须链接替代文档。
- `Archived`：仅供历史查询，不可作为实现依据。

禁止使用混合状态，例如“已批准（草案）”。

## 3. 现行文档的最小元数据

每份现行文档开头必须说明：

```md
- 类型：领域 / 产品 / 技术 / 决策
- 状态：
- 面向读者：
- 本文规范什么：
- 不规范什么：
- 规范来源或替代关系：
- 最后确认日期：
- 未决项：
```

无未决项时，明确写“无”。

## 4. 内容职责

- 领域文档只定义稳定的业务语义和边界。
- 产品文档只定义用户目标、流程、规则和验收结果。
- 技术文档只定义实现方式和工程约束。
- 决策记录只保留取舍依据；被替代后不得继续作为现行规范。
- 调研、会议纪要和原型说明不得替代以上任一现行文档。

业务规则优先使用编号、表格或示例表达；背景仅保留理解决策所必需的内容。

## 5. 变更要求

变更一条规则时，必须：

1. 先更新该规则的现行规范来源。
2. 同步受影响的引用、术语或技术文档。
3. 将旧文档标记为 `Superseded` 或 `Archived`，并写明去向。
4. 不得留下“请以另一篇文档校正本文”的说明。

“计划”“已确认”“已实现”和“已验证有效”必须分别表述，不得互相替代。

## 6. 项目采用声明

采用本标准的项目应在其工程标准声明中说明：

- 各类现行文档的位置；
- 文档负责人或评审责任；
- 历史文档的归档位置；
- 文档与代码发生分歧时的处理方式。
