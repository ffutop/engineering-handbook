# 文档治理标准

本标准定义团队项目中设计、架构和工程文档的最低治理要求。项目的目录结构、工具和审批流程可自行决定，但不得与本标准冲突。

## 1. 规范来源

每个项目必须为以下范围指定唯一的现行规范来源：

| 范围 | 规范内容 |
|---|---|
| 领域 | 术语、对象、状态和跨模块边界 |
| 产品 | 用户、流程、业务规则和验收边界 |
| 技术 | 数据结构、接口、部署和实现约束 |
| 决策 | 方案选择的理由、代价和替代关系 |

一条规则只能有一个现行规范来源。其他文档可以引用或解释该规则，但不得给出相冲突的版本。

## 2. 文档状态

文档只使用以下状态：

- `Proposed`：待确认。
- `Accepted`：已确认，是当前设计或工程约束；实现进度单独记录。
- `Implemented`：兼容既有文档的状态，表示已确认且已实现；新文档使用 `Accepted`，实现与验证证据单独记录。
- `Superseded`：已被替代，必须链接替代文档。
- `Archived`：仅供历史查询，不可作为实现依据。

禁止使用混合状态，例如“已批准（草案）”。

## 3. 现行文档的最小元数据

每份现行文档开头必须说明：

```md
- 类型：领域 / 产品 / 技术 / 决策
- 状态：
- 负责人：
- 适用范围：
- 面向读者：
- 本文规范什么：
- 不规范什么：
- 规范来源或替代关系：
- 最后确认日期：
- 实现情况与验证证据：
- 未决项：
```

无未决项时，明确写“无”。

## 4. 内容职责

- 领域文档负责定义稳定的业务语义和边界。
- 产品文档负责定义用户目标、流程、规则和验收结果。
- 技术文档负责定义实现方式和工程约束。
- 决策记录保留问题、选项、取舍与结果，引用规则的现行规范来源；被替代后不得继续作为现行规范。
- 文档可包含理解其职责所必需的上下文；跨职责规则采用链接引用，不要求为每段背景另建文档。
- 调研、会议纪要和原型说明不得替代以上任一现行文档。

业务规则优先使用编号、表格或示例表达；背景仅保留理解决策所必需的内容。

## 5. 变更要求

变更一条规则时，必须：

1. 在同一变更中更新该规则的现行规范来源；实现与文档须协调生效，未实施部分明确记录。
2. 同步受影响的引用、术语或技术文档。
3. 仅在整份文档失去现行效力时，将旧文档标记为 `Superseded` 或 `Archived` 并写明去向；局部变更保留现行状态，通过 Git 历史追溯。
4. 不得留下“请以另一篇文档校正本文”的说明。

“计划”“已确认”“已实现”和“已验证有效”必须分别表述，不得互相替代。

## 6. 项目采用声明

采用本标准的项目应在其工程标准声明中说明：

- 各类现行文档的位置；
- 文档负责人或评审责任；
- 历史文档的归档位置；
- 文档与代码发生分歧时的处理方式。

## 7. 冲突与例外

发现文档、代码与运行行为不一致时，记录差异、影响和责任人；运行行为是现状证据，不能自动覆盖已确认的约束。由负责人确认修复实现或变更规则，在同一变更中补充验证证据。

规范优先级、例外与标准升级遵循[规范治理标准](standard-governance.md)。文档状态不代替上线许可，也不代替测试结果。
